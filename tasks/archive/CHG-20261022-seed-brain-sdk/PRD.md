# PRD-20261022-seed-brain-sdk — 产品契约

> 本文件定义「对外承诺什么」。工程怎么实现见 SPEC.md；为什么做见 CHANGE.md。

## 1. 一句话定位

**把任意领域的知识，编译成智能体可无偏检索、可增量演进、可自我验证的「种子大脑」。**

不是又一个知识库，而是**知识库与智能体之间的检索层 + 验证层**。

## 2. 为什么它能提升任意 harness / 任意模型

这是本产品的核心命题，也是 README 要讲清的因果链：

| 环节 | 模型自己硬扛时 | 有种子大脑时 |
|---|---|---|
| **选风格/选工具** | 靠预训练语料里最高频的那几个（赛博霓虹、SVD） | 全库等距平铺 + IDF 加权，低频但精确的条目也能被选中 |
| **稳定性** | 同一个模型不同会话给出不同答案 | 确定性打分：同输入必得同输出，可复现 |
| **可解释性** | 说不出为什么选这个 | 每次输出命中信号与权重（`霓虹·4.3  长图·3.3`） |
| **积累** | 会话结束即遗忘 | 增量池 + 状态记忆，越用越准 |
| **防退化** | 无 | 38 项门槛断言 + CI，算法退化立即红 |
| **跨模型** | 强模型好、弱模型差 | 把「靠模型记忆」换成「查库 + 约束 + 自检」，弱模型也能拿到同样的候选集 |

**结论**：它不提升模型的推理能力，它**把「选什么」从模型权重里搬到可审计的数据里**。
所以收益与 harness 无关、与模型规模无关——这两个维度只影响「读库之后的多步推理」，不影响「选得对不对」。

## 3. 用户与场景

| 用户 | 场景 | 成功标准 |
|---|---|---|
| **领域作者**（想给自己的领域做种子库） | 有一批结构化知识（Markdown 章节 / 卡片目录） | 写一份 `profile.json`，30 分钟内跑出可检索索引与验证报告 |
| **agent 使用者**（Claude Code / Codex / pi / 自建 harness） | 任务开始前需要「选对方案」而不是「想一个方案」 | `seedbrain match "<任务>"` 直接给跨层均衡的 top-K |
| **维护者**（长期演进） | 发现某个选择不合适 / 想加新条目 | 一条 `add` 命令进增量池，立即生效；策展回填后计数闸门自动校验 |

## 4. 用户故事

- **US-1**：作为领域作者，我复制 `profiles/example.json`，改掉路径与正则，就能 `build` 出索引，**不写一行 Python**。
- **US-2**：作为 agent 使用者，我在任意 harness 里运行 `seedbrain match`，拿到带命中信号的候选列表，并知道每条来自哪个文件。
- **US-3**：作为维护者，我改一次 `score.py`，所有领域实例同步受益，不需要同步两个仓库。
- **US-4**：作为谨慎的使用者，我能在交付后 `pick` 记录使用，让刚用过的条目在 14 天内自然下沉，避免复读。
- **US-5**：作为审计者，我能在 CI 里跑 `seedbrain verify`，得到一份带门槛与实测值的报告，任何退化都让构建失败。

## 5. 功能需求

| ID | 需求 | 优先级 |
|---|---|---|
| FR-1 | `build`：解析 profile 声明的源 → 等距平铺索引（`.jsonl` 机器可读 + `.md` 人可读） | P0 |
| FR-2 | `match`：字符 2~3-gram + IDF 加权 + 跨层配额 → top-K，输出命中信号与 idf | P0 |
| FR-3 | `pick`：记录使用（次数 / 时间戳 / 评分），供时间衰减使用 | P0 |
| FR-4 | `add`：写入增量池，不改源文件；校验 `ref` 存在、同层查重（包含度 ≥ 阈值告警） | P0 |
| FR-5 | `verify`：可配置的门槛断言套件，输出 PASS/FAIL + 实测值 + 退出码 | P0 |
| FR-6 | `stats`：覆盖率审计（分层 / 分组 / 零使用盲区 / 复用最多） | P1 |
| FR-7 | 库 API：`SeedBrain.load(...)` 后可直接调用上述全部能力 | P0 |
| FR-8 | profile 校验：字段缺失/正则无效/源文件不存在 → 明确报错，不静默出空索引 | P0 |
| FR-9 | `--root` 支持驱动**外部仓库**（SDK 与内容分离的前提） | P0 |
| FR-10 | `ref` 越界防护：解析出的路径必须落在 root 内 | P0 |
| FR-11 | 索引漂移检测：`build` 幂等，CI 可 `git diff --exit-code` | P1 |
| FR-12 | 内容层校验（可选）：目录计数 / 六字段齐全 / 文档声明（由 profile 配置） | P1 |

## 6. 非功能需求

| ID | 要求 | 理由 |
|---|---|---|
| NFR-1 | **零第三方运行时依赖** | 无网 / 受限环境 / 供应链安全；`pip show` 的 Requires 必须为空 |
| NFR-2 | Python ≥ 3.9 | 覆盖面；因此配置用 JSON（`tomllib` 只有 3.11+） |
| NFR-3 | 确定性：同一输入必得同一输出 | 不用 `random`、不用内置 `hash()`（带随机种子）→ 用 `hashlib` |
| NFR-4 | 可解释：每次命中能列出 `(信号, 权重)` | 用户要知道「为什么是它」 |
| NFR-5 | 离线可用：CI 不联网取数 | 供应链 + 可复现 |
| NFR-6 | 规模：1e4 粒以内单次 `match` < 500ms | 会话内可接受的延迟 |

## 7. 数据契约

### 7.1 Seed（一粒种子）

```json
{
  "id": "cg-02-赛博霓虹",
  "name": "赛博霓虹",
  "layer": "code-gene",
  "group": "code-genes",
  "one_liner": "暗色 dashboard、科技产品长图…",
  "text": "赛博霓虹 科技 霓虹 暗色 …",
  "grams": 187,
  "ref": "references/code-genes/02-赛博霓虹.md",
  "origin": "source"
}
```

- `id` 全局唯一，含层前缀（如 `cg-`）；**一旦生成永不改写**（增量撞车加后缀，不覆盖）
- `text` 是唯一的匹配输入；`grams` 是长度缓存（用于归一化）
- `origin` ∈ {`source`, `addition`}

### 7.2 Profile（一份领域配置）

见 SPEC §4。要点：**SDK 里没有「领域」这个概念，只有 profile**。

## 8. 验收标准

| # | 标准 | 判定 |
|---|---|---|
| AC-1 | 新领域零改代码 | 只用 `profiles/example.json` 跑通 `build → match → verify` |
| AC-2 | 上游不回退 | 用 SDK 驱动美学大脑，27 项断言逐项与改造前一致 |
| AC-3 | 零依赖 | `pip show agent-seed-brain` 的 Requires 为空 |
| AC-4 | 无内容污染 | `git grep -l "赛博霓虹\|art-seeds"` 仅出现在测试 fixture 与 profile 示例中 |
| AC-5 | 首版即绿 | 首次 push 后 CI 全绿；无需要清理的失败 run |
| AC-6 | README 可独立理解 | 不读源码即可完成安装与第一次 `match` |
